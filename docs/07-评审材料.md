## 二、四条"新颖性 / 稳定性"核心叙事候选（配验证闭环）

写成叙事时用这个结构：**观察到什么 → 反直觉的结论 → 因此改了什么 → 验证结果**。

1. **"动作互斥 ⇒ 并发只能用来想，不能用来做"**
   官方给了 24 路并发，直觉是开 24 个 agent 并行干活。但规范 §0 写明同一 bot 一次只能一个动作且阻塞，
   所以真正的用法是"动作阻塞期间在另一个线程里算下一步"。→ 架构从"并行执行"改成"执行-思考重叠"。
   **待补**：一次动作的实际时长 vs 一次决策的延迟，两者重叠能省多少。

2. **用 `inspect.signature` 反射 + 强类型边界做决策校验，而不是手写白名单**
   模型最常见的坏输出是"发明不存在的方法"或传入布尔/NaN 异常参数。手写白名单会和 `client.py` 漂移；
   反射真实签名并叠加跨参数约束后，客户端加方法校验器自动跟上。→ 用一个轻量校验器消灭一整类失败。
   **已验证（offline）**：`code/tests/test_d0_core.py` 覆盖方法反射、缺参拦截与 `bool`/NaN 坐标阻断；**待补**：真机拦下的坏决策统计。

3. **分级验证准入（`verified: offline` / `verified: live`）：既防幻觉污染，又破单账号死锁**
   第一版骨架删掉了未上真机的技能与 LLM 模块（见 `docs/06` 11-12 23:35），同时针对单皮肤站账号独占约束，
   把协议/恢复逻辑纳入离线故障注入单测准入（`verified: offline`），把世界物理耦合技能留给真机准入（`verified: live`）。
   → 仓库里每行代码要么经过确定性故障注入单测验证，要么经过真机验证。

4. **HTTP 阻塞动作的"超时背包快照判重"与"条件变量紧急抢占锁"**
   在同步 HTTP 动作接口下，`craft` / `use_item` / `window_act` 网络超时处于"未知是否已执行"态，盲目重试会双倍消耗珍贵材料（如烈焰棒/末影之眼）；普通互斥锁又会让后台避险被长距离 `move_to` 阻塞。
   → 执行器在非幂等动作前采集背包快照，超时先 `/stop` 再比对快照恢复结果或转 `Replan`；同时通过 `Condition` + 抢占代次保证 `emergency()` 立即中断当前动作并优先于排队普通动作完成逃生。
   **已验证（offline）**：`code/tests/test_d0_recovery_and_preempt.py` 5 项故障注入单测全绿（见 `docs/06` 11-13 00:30）。

## 五、两个容易被扣分的地方（自查）

1. **报告里的数字没有出处**：任何数字都要能指到 `probe/*.json` 或 `docs/06` 的某条。
2. **"我们打算做"写成"我们做了"**：没跑通就写"设计已完成，未验证"，比含糊其辞安全得多——
   评委见过太多"预计实现"，写清楚边界反而显得可信。
