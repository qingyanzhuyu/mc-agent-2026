## 一、Harness 赛道条款（公告原文要点）

**定位**：赛事设 Harness 赛道、Model 赛道。看重技术创意、游戏内自主行为、互动性与观赏性，声明"不将单一任务完成率、固定模型基准作为唯一评判标准"。

**组队**：1–4 人。队长必须是南大在校生；队员身份不限，可外校。

**模型（硬约束）**
- 统一模型 **DeepSeek V4.1 Flash**，走 AIA 提供的统一代理 API。
- 不得改用其他大模型，不得通过外部服务绕开额度约束。

**参赛内容（自建）**
自行设计 Harness：规划调度、记忆、工具调用、状态维护、行为策略、多 Agent 协作等；
统一通过 **NMO 接口** 操控 Minecraft Agent。

**赛制**
- 11/18 完成报名与初赛材料收集。
- **11/22（周日）10:00–18:00 初赛**，8 小时，共享世界实战，选 8 队进决赛。
- 比赛内允许改提示词、调框架、重启程序；**禁止参赛人员直接代替 Agent 执行游戏行为**。
- 12/6（周日）10:00–18:00 双赛道共享世界决赛，最多 16 队同场。

**资源额度（每队）**

| 资源 | 初赛 | 决赛 |
| --- | --- | --- |
| 运行窗口 | 8 小时 | 8 小时 |
| 输入 Token | 800 万 | 1,000 万 |
| 输出 Token | 150 万 | 200 万 |
| 最大并发请求 | 4 | 4 |

赛前另有 **50 万输入 / 10 万输出** 的统一联调额度。按 API 返回 usage 统计，输入输出分别硬限额。
注：赛前压测若需调整配额，会两赛道同时调整并提前公告（"配额有很大概率上升"）。

**环境与互动原则**
- 每场一套独立生存世界，同场全部 Agent **共享同一世界**、同时存在、自由行动，不分队开副本。
- 初赛、决赛各新建世界，避免前期资源积累带来优势。
- MC Advancement 是参考主线，不强制；可自选建筑、农业、红石、下界探索、屠龙、协作或自创目标。
- 允许正常资源竞争与自愿协作；禁止利用漏洞、观众操控、人工代打、攻击基础设施、**持续性阻止其他 Agent 正常比赛**。PvP/破坏/资源争夺的边界由 NMO 提前公布并执裁。
- 观众只能观察者身份，不得产生物品/改世界/发指令。
- 服务器监控 + 世界快照（建议每 15–30 分钟）；崩服/大规模恶意破坏由裁判组决定暂停、修复、回滚或调整剩余时间。

## 二、初赛计分细则（细则页原文要点）

**总成绩 = 游戏表现分（60）+ 工程评审分（40）**，百分制，保留两位小数，作为初赛排名主要依据。

### 1. 游戏表现分（60）

- 只统计赛前公布的原版**非配方** advancement；配方解锁、自定义 advancement、比赛时间外完成的不计分；同一项只计一次。
- 单项分 = **难度基础分 + 5 × 进度树深度**
  - 难度 1 = 5，2 = 15，3 = 30，4 = 60，5 = 100
  - 深度从各分类根节点起算，根节点深度 0（根节点本身 0 分）
- 游戏原始分 = 8 小时内所有计分 advancement 分值之和
- **游戏表现分 = 本人原始分 ÷ 本届最高原始分 × 60**（全场最高者得 60，其余按比例折算；全员 0 则全 0）
- 完成状态与完成时间以服务器记录为准，客户端/自报/本地日志不算。

### 2. 工程评审分（40）

- ≥3 名评委，各自 0–40 分；去掉一个最高、一个最低，其余取算术平均，保留两位小数。
- 考察：harness 与 Agent 整体设计完善性 / 方案策略技术的新颖性 / 工程结构、代码组织、实现逻辑清晰度 / 稳定性、可复现性、可维护性等综合工程表现。

### 3. 并列判定

游戏表现分 → 难度 5 数量 → 难度 4 数量（依次向下）→ 更早达到最终原始分 → 并列。

### 4. 其它

- "赛事 API 不保证能够完成游戏中的每一个原版 advancement，参赛者应根据公开接口的实际能力自行选择任务和制定策略。"
- 8 小时内因参赛程序/网络/模型服务造成的中断**仍计入比赛时间，不补时**；仅赛事服务器统一故障才可能暂停/补时/重赛。
- 赛后公布原始分、表现分、工程分、总成绩及已完成 advancement 与完成时间；有申诉期。
- "决赛的比赛形式、计分方式及具体规则将另行通知。"

## 三、评价

### 设计得好的地方

1. **统一模型 + 统一接口 + 统一额度 = 真可比**。这是这类比赛最容易烂掉的地方（"谁模型大谁赢"），这里被彻底钉死了。再加上每场新世界、赛前重置出生点/背包/经验/进度，可比性和反"带号进场"都做到了。
2. **60/40 的结构是对的**。纯看游戏分会退化成"抄一个强 macro"；纯看工程分会变成写 PPT。60 分实打实的世界内产出 + 40 分工程评审，逼你把"能跑"和"设计得好"同时做出来。
3. **配额 + 并发 4 这两个约束才是真正的题目**。8M/1.5M 的预算下，逐 tick 调 LLM 是不可能的，你必须做分层控制（大模型当规划器、确定性脚本当手脚）、观测压缩、预算治理。这比"写个好 prompt"有意思得多，也正好对上公告说的"产出可复用的 Agent 评测接口/流程"。
4. **反作弊设计干净**：只认服务器记录、不看客户端；状态赛前统一重置；观众隔离；快照 + 回滚。
5. **评委机制有统计常识**：≥3 人、去极值、并列用逐级 tie-break（而不是简单并列）。
6. **门槛低**：只要一台能跑 8 小时的机器 + API，不需要显卡（显卡是 Model 赛道的事）。

### 真正的问题（按严重度）

1. **公告和细则在"怎么评"上互相打架。**
   公告说"参考世界内表现、**创造力、稳定性及可观赏性**等综合评议，选出 8 支"、"不将单一任务完成率作为唯一评判标准"；
   细则说"总成绩 = 游戏表现 60 + 工程评审 40，作为排名主要依据"，而 40 分里根本没有"创造力/可观赏性"这一项（只有完善性/新颖性/清晰度/稳定性）。
   结果：按公告优化（做观赏性、做创意玩法）和按细则优化（刷 advancement + 交漂亮工程）是两条不同的路。**目前应以细则为准**，但这属于必须澄清的口径问题。

2. **60 分是相对分，这个设计会放大运气、也会奖励"压制对手"。**
   `本人原始分 ÷ 全场最高 × 60` 意味着：只要有一队打出碾压局，其余队的 60 分被整体压扁，第二名和第五名的差距可能完全由那一队的发挥决定。
   更麻烦的是它在共享世界里把"拖住别人"变成了理性策略——你的分母是别人的分子。而规则只禁"**持续性**阻止其他 Agent 正常比赛"，"把村里的牛全杀了""把村子围起来"算不算，边界是模糊的。这是本次规则里最需要补的一条。

3. **四个关键件到现在（11/3，距初赛 19 天）都还没发布**：
   - NMO 的**统一接口文档 / 示例 Agent / 本地测试服**（"另行发布"）—— 这是唯一的硬依赖，没有它没法开始真正的工程
   - 赛前**计分表**（每项 advancement 的难度与深度，"以计分表为准"）
   - **工程评审要交什么**（仓库？报告？录像？截止时间？细则只说"对提交的 harness 和 Agent 工程进行评审"，提交物形态未定义；而 11/18 就要"完成初赛材料收集"）
   - **决赛规则**（"另行通知"，而决赛 12/6）
   对 8 小时直播赛来说，接口文档晚一周 ≈ 少一周迭代，这是最大的执行风险。

4. **"API 不保证能完成每一个 advancement" 是一颗定时炸弹。**
   这话很诚实，但它意味着**分数上限由接口的动作空间决定，而不是由你的 Agent 决定**，而这个能力边界没有公开。于是比赛第一小时变成了"试探 API 能干什么"，而最终排名在很大程度上取决于"谁先摸到 API 的甜点"。作为一次活动这很刺激；作为一个"评测基准"（公告的目标之一）就偏了：换一届 API 变一点，成绩不可跨届比较。

5. **一次 8 小时、不补时、无练习赛 → 稳定性远比聪明重要，但这一点只值 40 分里的半项。**
   程序崩了、网断了、模型服务抖了，都算你的时间。一次开局 30 分钟的崩溃就丢掉 7.5 小时和 60 分里的大头。而这类"运维能力"只在工程评审的"稳定性"四个字里被轻描淡写地提了一次。**理性的最优解其实是"把 60 分保底、把花活放到能保底之后"**，但规则没有明说，很多队会死在过度设计上。

6. **观赏性和赛制自相矛盾。**
   文本模型 + 8M/1.5M 预算下，Agent 的决策节奏大约是 6–8 秒一步，在 MC 里看起来是个动作极慢、走走停停的玩家。公告却把"观赏性"写进目标、还要直播剪片。初赛 40 分里又不含观赏性 → 团队理性上不会为观赏性花成本。想清楚"是比赛还是表演"，或者给观赏性一个明确的加分位。

7. **小口径问题**：advancement 树有不少多父节点，"进度树深度"对多父节点怎么算没定义（好在细则把最终值推给了计分表，但计分表也没发）；"不得改用其他大模型"是否允许本地小分类器/embedding/RL 策略，没有说清。

## 四、Token 预算测算（初赛 8M in / 1.5M out / 28,800 秒）

平均可持续速率：输入 ≈ 278 tok/s，输出 ≈ 52 tok/s。

| 单步开销 | 步数上限（输入/输出） | 折合节奏 |
| --- | --- | --- |
| 2,000 in + 400 out | 4,000 / 3,750 → **≈3,750 步** | 每 7.7 秒一步 |
| 4,000 in + 500 out | 2,000 / 3,000 → **≈2,000 步** | 每 14 秒一步 |
| 8,000 in + 800 out（中等粒度，每 30 秒一次） | 1,000 / 1,875 → **≈1,000 步** | 30 分钟就烧掉 1/3 输入 |
| 12,000 in + 1,500 out × 96 次（每 5 分钟一次规划） | 仅占 1.15M 输入 | 便宜 |

**结论：能活的两种形态是"极小的反射步"和"极少的大规划步"；死在中间——中等粒度、中等频率的调用最烧钱。**
另外 输入:输出 = 5.3:1，而典型 Agent 的输入输出比是 8–15:1，**输入几乎一定是先撞墙的那一侧**：观测必须结构化压缩（状态摘要而非原始文本堆），记忆要主动总结，工具返回要短。

## 五、如果我要参赛，优先级排序

1. **接口适配 + 断线/崩溃恢复**（8 小时一次机会，这条比什么都重要：存档、重连、幂等动作、watchdog）
2. **预算治理器**（按步记账、95% 硬停、异常重试熔断、输入/输出分开算）——没有它，一个 bug 循环能在 10 分钟烧光 8 小时
3. **低层技能库**（砍树/挖矿/合成/移动/战斗的确定性脚本），让 LLM 永远不碰原始动作
4. **规划器**（读计分表做性价比排序：单项分 = 难度基础分 + 5×深度，深度大的链式进度性价比常常高于单点高难度）
5. **观测压缩**（≤1k token 的结构化状态：背包、坐标、生物群系、当前目标、最近 N 条事件）
6. 4 并发可以用来开 4 个子 Agent（探索/建造/战斗/后勤），但共享同一份预算，要先算清分配

## 六、需要向主办方（NMO / AIA）确认的清单

1. 统一接口文档、示例 Agent、本地测试服，**什么时候发**？
2. 赛前计分表（每项 advancement 的难度与深度）什么时候发？多父节点的深度怎么算？
3. 工程评审（40 分）**提交物是什么**（仓库/报告/录像）、截止时间、是否要求提交源代码？11/18 的"初赛材料"对 Harness 赛道具体指什么？
4. 公告的"创造力/可观赏性综合评议"与细则的"60+40 百分制"，**哪个为准**？
5. 决赛的赛制与计分（"另行通知"）什么时候公布？
6. PvP / 破坏 / 资源争夺的具体边界：**"资源剥夺"（清空牛群、围村、堵矿洞）算不算"持续性阻止其他 Agent 正常比赛"**？
7. "不得改用其他大模型"是否允许在 Agent 内部使用本地小模型（分类器/embedding/RL 策略）做感知或低层决策？
8. 统一代理是否支持 **prompt caching**，缓存命中部分是否计入额度？（直接影响 8M 怎么花）
9. 50 万 / 10 万联调额度什么时候可用？赛前有没有一次练习赛/沙盒世界？
10. 并发 4 是硬限（超了返回 429）还是软限？是否按 key 计？
11. 决赛两赛道同场时，Harness Agent 与 Model Agent 能否互相 PvP / 抢资源？
12. 是否提供托管运行环境（消除家庭网络/机器休眠这类非技术风险）？
